# 测试全绿说明不了什么:从 29 条检视 gap 到真实使用的闭环

> 项目写完 v0.4.0,README 该说的都说了。然后我把整个仓库(~30k 行 Rust)丢给一次系统性检视,挖出 29 条 gap —— 有超卖的文档、有 Windows 上根本跑不了的代码、有承诺了没兑现的安全校验。这篇讲的不是那 29 条本身,而是背后那条**验证链**:声称 → 证据 → 修复 → gate → 真实使用,每一层怎么设计才不自欺 —— 以及,诚实地,每层各抓到过什么、还没抓到过什么。

## 先承认:测试全绿说明不了什么

这个项目当时有 400+ 个 Rust 测试,clippy `-D warnings` 全绿。检视开始前的第一句话就是:这只说明**我想到要测的东西都测了**,不说明:

- 我没想到的 —— 没测
- 我刻意没测的:仓库在 Linux 上开发,测试用了 unix 的 `sleep`/`true`/`/proc`,Windows 上**从来没跑过**
- 文档说的和代码做的(README 写「真拉 Prometheus」,manifest 注释写着 OOMKilled 没入图)—— 没人对过

所以检视的方法论第一条:**声称必须落到 file:line**。六个维度(分发/显式债务/首启体验/安全/文档承诺/平台)并行读源码,每条 finding 都要求给出真实读到的位置 —— 凭 README 印象说的不算。第二条更关键:**对抗核实**。协议是这样的 —— 核实者只拿 claim 和它的 file:line,**不给检视者的推理过程**(给了就会顺着推理找);权限是全仓只读;判决三态:杀(声称的缺口其实已实现)/ 修(证据在但描述偏)/ 立(站得住)。这一轮杀掉了谁?一条都没全杀,但「修」了几处 —— 比如把「集群配置散在多处」修正为确切的 5 处内联 config。这轮的产出不是戏剧性的打脸,是一个性质:**过了这关的每一条,我都反驳不掉。** 也要诚实记下它的局限:同一个脑子产出的怀疑者,继承同一个盲区 —— 同源偏见没有消除,只是收窄。

## 修复的纪律:按根因分批,不按发现顺序

29 条不是 29 个独立改动。聚类下来是五批:平台兼容、安全边界、分发链路、健壮性、文档校准 —— 按批走,每批一个 gate(全量测试 + clippy + 前端),批内修完再进下一批。两个例子说明这种打法为什么必要。

**例一:同一个根因,三处症状。** 分发链路看着是三个问题:安装包不含 WASM 模块、release 二进制只认编译机路径、集群配置散在五处。根因是一个:**「能在开发机上跑」和「能被别人用」之间,从来没有一条被验证过的路**。修复就是把这条路补通(打包、路径解析、配置收进 manifest 的 `[defaults]`,各补一刀)。分批的意义在这里:按发现顺序东修一个西修一个,三处症状会被当成三个独立 bug,根因继续漏。

**例二:测试的假绿比不绿更危险。** `fs-read` 的路径校验([capability 沙箱那篇](./02-wasm-capability-sandbox.md)讲过的 `resolve_and_check`,在 `engine-wasm/src/fs_host.rs`)在 Windows 上恒拒绝一切合法请求。一个坑:Windows 的 `canonicalize` 会给绝对路径加 `\\?\` verbatim 前缀 —— 同一份代码,两个平台吐出不一样的「同一路径」:

```text
Linux  : /home/me/code/otel-demo/src/lib.rs
Windows: \\?\C:\Users\me\code\otel-demo\src\lib.rs
```

root 是按普通形态 canonicalize 的,请求路径带着 `\\?\` 前缀,组件级 `starts_with` 匹配不上 —— 恒 false。而它的测试在 Linux 上全绿(Linux 没这个前缀),在 Windows 上从没跑过。修复代码只花十分钟,真正的修复是让 Windows 变成一级测试平台 —— 这就引出下一层。

## gate 要抓过血,才算 gate

CI 不是写完 workflow 就完事。这个项目的 CI 七个 job(含一个 Windows job),**三轮才绿,每一轮的失败都是真信息**:

- 第一轮:**新版 clippy 抓出本机没有的 lint**(`double_must_use`,打在 `#[async_trait]` 宏展开处)。本机工具链 1.98,CI 是最新 stable —— 「本地绿」和「CI 绿」中间隔着一个工具链版本的时差,这个时差只有真跑 CI 才暴露。
- 第二轮:逐处补 allow 修不干净 —— 同一 lint 打在**所有** async 宏展开点,升为 crate 级 allow 才了。局部修补掩盖系统性误报,这是第二次被提醒。
- 还是第一轮挂的:一个坑 —— tauri 的 `bundle.resources` 引用 modules 的构建产物(`glob pattern .../*.wasm didn't match` 直接报错),但 CI 上 modules 是独立 job,没人在 desktop 前构建它。这个失败把一条**一直存在但没人写下来的构建依赖**显式化了:desktop 构建前必须先 build modules。README 的构建顺序一直是这么写的;CI 的价值是让违反它的代价立刻可见。

第三轮全绿。但要说清楚 Windows job 的位置:**它至今全绿、没流过血 —— 按我自己的标准,它还是候选 gate,不是 gate。** 检视挖出的那批 Windows bug,是读源码发现的,不是它拦下的。让它转正的只能是它拦下的第一条 Windows-only 回归。

同理,发版流水线也是三轮:第一轮死在 UTF-8 BOM(PowerShell 写文件带的,JSON 解析器撞死),第二轮死在 tauri-action 缺 `GITHUB_TOKEN`。三轮之后四平台产物落进 draft release。发版流程没有「应该能跑」这个状态,只有跑过和没跑过。

## 真实使用是最硬一层:上线十分钟连抓两个 bug

发完版我把应用挂到真实集群常驻运行(真实 alertmanager,挂着 11 条 active 告警)。上线十分钟,连抓两个 bug,都在 alertmanager connector 这个最新写的模块里。

**第一个:API 响应形态想当然了。** 一个坑:Alertmanager v2 的 `/api/v2/alerts` 返回的是**顶层数组**,而我的反序列化按对象包裹写的:

```jsonc
// 我以为的                // 实际的
{ "alerts": [ ... ] }      [ ... ]
```

静默失败,错误进了状态表但不打日志,产出恒为零。单元测试全绿 —— 因为 fixture 是照我的错误假设造的。**fixture 形态没对过真数据,测试只是在验证我的误解。**

**第二个:语义拷贝没过脑子。** 我把 k8s-events connector 的 baseline 模式(首轮静默,防重启录历史)照搬给了 alertmanager。但 Warning **事件**是历史流(首轮静默合理),alerts 是**当前活动集** —— 打开应用就该看到现存告警。照搬的后果:重启后 11 条存量告警永远静默,这个应用挂一年也显示零告警。

两个 bug 的位置要分开说:第一个有测试罩着,fixture 造错了形状;第二个那段编排逻辑**压根没有测试**。共同点是两个 bug 都活在测试全绿的模块里。这说明单测的边界在哪 —— 它验证代码做的是「测试以为它该做的事」,而「该做的事」只有真实数据能定义。这不是贬低测试:第一个 bug 的修复是「顶层数组解析 + 对象包裹必须 parse 失败」的防退化断言钉死的,第二个是 fingerprint 稳定 id(幂等键)的断言。**测试不负责发现语义错误,负责把发现后的修正焊死。** 而焊死的效力取决于焊进去的真相从哪来 —— fixture 必须抽自真实 payload 并注明来源,否则只是把今天的误解换成昨天的。

同一晚还抓了第三个:裸 `cargo build --release` 出的调试 exe,窗口打开是白屏占位页 —— 它不跑 `npm run build`,把 dist 里当时的占位文件嵌进了二进制。这其实是分发链路那批的回响:**「能跑」和「被验证过能跑」之间的路,永远有新的岔道**。修复落在文档层(README 显式警告)+ 你的眼睛。

最后补一段挂机的方法论。这层凭什么抓到血?两个 bug 都是靠「挂上去之前就知道集群里有 11 条 active 告警」这个**独立于代码的预期**才现形的 —— 没有这个锚,「零告警」看起来完全正常,真实使用这层同样会假绿。挂任何东西之前,先写下你预期它该显示什么。

## 那条链,以及每层真实的战绩

回头看,这轮工作真正搭起来的不是某个功能,是一条链。链有五环,但流的血都在关节上 —— 表格按关节列(修复这环的血由它的批次 gate 代持,gate 这环裂成 CI 和发版两处):

| 关节 | 抓到过什么 |
|---|---|
| 检视(file:line + 对抗核实) | 29 条 gap:文档超卖、Windows 假绿、承诺未兑现 |
| 修复批次 gate | **没有 —— 这层至今没流过血。** 它的绿只值「五批互不相踩」,不说明没引入新问题;从未失败过的 gate,它的绿是未定价的 |
| CI | 工具链时差的 lint、构建依赖的违反(Windows job:候选,未流血) |
| 发版流水线 | BOM、token —— 只有跑过和没跑过 |
| 真实使用(挂机) | 语义错位、fixture 形态错误、占位页 —— 靠「预先写下的预期值」现形 |

如果只能带走一句:**设计决定一个 gate 能抓哪类错,战绩证明它真抓到过 —— 前者是潜力,后者是资质;没流过血的 gate,和纸面设计一样是装饰。** 而且血是会过期的:工具链在漂,fixture 会烂 —— 本机绿/CI 抓血的那次就是证明,一个曾经流血的 gate 也会重新失明。这条链现在多数关节流过血,但它只在下一次还流血时才算活着。每层的血还标着错误的类型:工具链时差和构建依赖归 CI,语义错位和形态错误归真实使用,回归归单测,超卖归检视 —— 下一个 bug 冒出来,先看它是什么类型,再选层。
